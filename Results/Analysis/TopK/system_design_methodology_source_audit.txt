A. CANDIDATE RANKING
====================

1. Exact Bayesian ranking key

Direct answer: Bayesian candidates are ranked lexicographically by

    (-local target probability, Manhattan distance from the robot's current cell, (x, y)).

Thus larger local probability is preferred, then shorter Manhattan distance, then smaller x, then smaller y. The filter does not rank by A* path cost, probability-adjusted allocation cost, insertion cost, or allocator utility. Those quantities may be used later by the allocator after filtering.

Evidence: Simulation/Architecture/simulator/benchmark_sim/algorithms/base.py -- AllocatorBase._filter_candidate_cells, lines 139-157; _filter_probability, lines 159-174; _manhattan_distance, lines 293-295. The production packed implementation expresses the same order explicitly in PackedCandidateMixin._candidate_precedes at Simulation/Architecture/simulator/benchmark_sim/algorithms/memory_optimized.py, lines 159-176.

Platform differences: AGX base and optimized Bayesian implementations use the above x-then-y tie-break. Generated RP2040 CBAA/ACBBA/PI/HIPC and DGA inherit the same logical order; native RP2040 DMCHBA implements probability descending, distance ascending, x ascending, y ascending in device/native/bayesian/dmchba_complete.py, lines 436-453. Physical Pololu programs duplicate the same tuple; for example Hardware/Algorithms/Pololu_CBAA.py, lines 1497-1513. Numerical representations differ across platforms, as detailed in answers 35-36.

2. Exact Collaborative Visit ranking key

Direct answer: The AGX Collaborative Visit key is also

    (-local target probability, Manhattan distance, (x, y)).

Active targets are initialized/evaluated with equal mission probability in the standard known-target visit condition, so Manhattan distance is normally the effective primary key, followed by x then y.

Evidence: Simulation/dcta_benchmark_sim/known_visit_sim/algorithms/base.py -- AllocatorBase._filter_candidate_cells, lines 154-172. RP2040 native code: Simulation/Architecture/allocator_replay/device/native/collaborative/base.py -- NativeAllocatorBase.candidates, lines 17-41.

Platform differences: RP2040 collaborative code uses encoded target cell ID as the last key, not the coordinate tuple: (-probability, distance, y*grid_size+x), base.py lines 24-34 and state.py lines 71-100, 160-178. Therefore its exact-tie order is row-major y then x. The AGX order is x then y. This is a confirmed semantic difference for equal-probability, equal-distance targets. No collaborative physical-testbed campaign exists in the supplied results.

3. Distance used by the filter

Direct answer: Manhattan distance from the robot's current logical cell to the candidate. It is not A* distance, probability-adjusted edge cost, or route insertion cost.

Evidence: Bayesian base.py lines 148-153 and 293-295; Collaborative base.py lines 163-170 and 275-277; packed Bayesian memory_optimized.py lines 228-245; native collaborative state.distance as invoked by native collaborative base.py lines 25-31.

Platform differences: AGX, HIL, and physical Bayesian filters all use Manhattan distance. Later allocator scoring/path planning differs and may use probability-adjusted cost or insertion cost, but that occurs after the filter.

4. Per-robot/local ranking

Direct answer: Yes. Each robot independently constructs and ranks candidates using its own current position, local searched/completed belief, and local probability/target state.

Evidence: Both base filters receive robot and read robot.pos and robot.target_p (Bayesian base.py lines 139-174; collaborative base.py lines 154-188). HIL snapshots one resident robot context at a time and calls that context's allocator (device/common/replay_persistent.py lines 273-314 and 417-428).

Platform differences: AGX stores local robot state in the simulator process; HIL stores/restores each logical robot's allocator context on an RP2040; physical robots maintain their own maps locally. The logical rule is the same, but message timing and local-belief divergence are physically real only on the testbed.

5. Deterministic tie-breaking

Direct answer: AGX Bayesian and Collaborative use coordinate tuple (x,y), i.e. x first then y. Generated/native Bayesian HIL and physical Bayesian use the same x-then-y rule. Native collaborative HIL uses encoded row-major cell ID y*grid+x, i.e. y first then x. Robot ID is not part of the candidate-filter tie-break.

Evidence: Bayesian base.py lines 150-155; memory_optimized.py lines 159-176; native Bayesian DMCHBA lines 436-453; physical CBAA lines 1507-1511; native collaborative base.py lines 24-31 and state.py lines 160-178.

Platform differences: The collaborative HIL row-major tie-break is the material cross-platform exception. Stable input order only governs the unrestricted pass-through case when no sort/selection is performed.

6. Determinism when ranking values tie

Direct answer: Yes within each implementation, because a final coordinate or cell-ID key resolves exact value/distance ties. However, AGX Collaborative and RP2040 Collaborative can deterministically choose different candidates because their final key orders differ.

Evidence: Same regions as answers 1, 2, and 5. Candidate scans are also deterministic nested-grid or sorted-target scans (memory_optimized.py lines 230-246; collaborative state.py lines 71-100).

Platform differences: Determinism is supported per platform; identical cross-platform ordering is not fully supported for Collaborative Visit exact ties.

B. DEFINITION AND APPLICATION OF K
==================================

7. Percentage-to-K conversion

Direct answer: For the 19x19 Bayesian grid,

    K = max(1, int(361*r + 0.5)),

where r is the retained fraction. For positive values this is round-half-up, not Python banker's round. Collaborative Visit uses the same precomputed rule against 50 initial targets:

    K = max(1, int(50*r + 0.5)).

Evidence: Simulation/Architecture/simulator/benchmark_sim/run_trials.py -- resolve_top_k_settings, lines 66-76; run_topk_campaign.py -- top_k_cells, lines 102-115. Collaborative fixed values are recorded in Simulation/Architecture/allocator_replay/config/study.py, lines 30-38, and Simulation/Studies/hil_aligned_simulation/core.py, lines 83-86 and 250-295.

Platform differences: AGX runners calculate/store the absolute K before a trial. HIL manifests transmit that fixed integer. The physical hub transmits a fixed top_k_cells value. There is no per-call percentage conversion on an RP2040.

8. Basis from which K is calculated

Direct answer: K is fixed from the scenario's maximum/initial basis: 361 grid cells for Bayesian search and 50 initially known targets for Collaborative Visit. It is not recalculated from the current valid-candidate count.

Evidence: run_trials.py lines 66-76; hil_aligned_simulation/core.py lines 235-238 (top_k_basis="grid_cells") and 292-295 (top_k_basis="initial_targets"); config/study.py lines 19-38.

Platform differences: Same fixed K is passed to AGX, HIL, and physical Bayesian runs. Current candidate count only determines whether filtering is a pass-through.

9. Minimum retained count

Direct answer: Configured percentage conversion always yields at least K=1. If there are zero valid candidates, the returned candidate list is still empty; the code does not fabricate a candidate.

Evidence: run_trials.py line 73; run_topk_campaign.py line 103; base filters lines 139-157/154-172.

Platform differences: Same logical behavior on all platforms.

10. Pass-through when current count <= K

Direct answer: Yes. The base implementations return all current candidates without truncation when limit is absent or limit >= current count.

Evidence: Bayesian base.py lines 139-146; Collaborative base.py lines 154-161; packed Bayesian memory_optimized.py lines 248-267; native collaborative base.py lines 21-36; physical CBAA lines 1497-1506.

Platform differences: The ordering/work performed in that pass-through case differs as described next.

11. Work performed in the pass-through case

Direct answer: It is implementation- and allocator-dependent.

* Base AGX and physical full-list implementations collect/copy the candidate list but do not compute the ranking key or sort when count <= K.
* Optimized packed Bayesian CBAA/ACBBA/PI still compute probability and Manhattan distance for every valid candidate during collection, but do not run bounded selection when count <= K.
* Packed Bayesian HIPC uses always_rank=True and ranks even at 100%.
* DGA and reference HIPC pre-rank their candidates before passing them to the base filter, so ranking can occur even when the base filter passes through.
* Native collaborative CBAA/ACBBA/PI/DMCHBA do not sort in pass-through; native HIPC and DGA call candidates(always_rank=True) and do sort.

Evidence: memory_optimized.py lines 218-267 and HIPC mixin lines 369-385; DGA.py lines 505-521; native collaborative base.py lines 17-36, hipc.py line 70, dga.py line 60; physical CBAA lines 1497-1513.

Platform differences: Therefore "100% has zero filter work" is false. Candidate discovery/validity work is always timed, and some allocators still rank at 100%.

Direct answer: Yes. It is labeled "K=1" and stored with an exact fixed fraction (1/361 Bayesian, 1/50 Collaborative), distinct from Bayesian "1%" (K=4). Collaborative also has fixed "K=2" (2/50=4%).

Evidence: config/study.py lines 19-38 and Condition.slug, lines 73-87; hil_aligned_simulation/core.py lines 78-86.

Platform differences: The distinction is preserved in simulation and HIL manifests/results. No physical K=1 validation was run.

C. INTERACTION WITH ALLOCATOR STATE
====================================

15. What filtering can remove

Direct answer: The filter restricts candidates admitted to a new allocation/reallocation solve. It does not globally delete winner tables or received messages merely because a task is outside Top-K. Its effect on stored paths is allocator-specific:

* CBAA: a valid, currently owned destination is returned before candidate filtering; Top-K gates only a new claim.
* ACBBA and PI: repaired committed prefixes remain, and Top-K gates refill/insertion candidates.
* HIPC: rebuilds a local team plan from the current restricted list, so a previously planned future cell can disappear when the bundle is replaced.
* DMCHBA: follows its stored path until a normal trigger; at reassignment, Top-K defines Hungarian tasks and therefore assignments/matrix dimensions.
* DGA: at reallocation, repair removes chromosome tasks not in the restricted candidate set and fills from that set; its committed path can consequently change.

Evidence: CBAA.py choose/claim region lines 130-177; ACBBA.py bundle repair/build lines 75-157; PI.py lines 112-203; HIPC.py lines 92-155 and 277-312; DMCHBA.py lines 85-230 and 449-457; DGA.py lines 283-304 and 383-420.

Platform differences: Generated Bayesian HIL follows these logical paths except native DMCHBA has a packed equivalent. Native Collaborative and physical standalone implementations are separate ports; they implement the same broad retention/replanning model but are not byte-identical.

16. Protection of current destinations

Direct answer: Generally yes. Current destinations/committed leading tasks are retained until completion, local invalidation, collision/replan handling, loss through normal consensus/deconfliction, or an algorithm-defined reallocation trigger. Top-K alone does not evict CBAA's current valid task.

Evidence: CBAA.py current assignment resolution region lines 130-177; physical CBAA _pick_task_cell_impl lines 1711-1735. ACBBA/PI repair their existing paths before refill; DMCHBA _reallocation_trigger lines 136-165 and _prune_invalid_path lines 449-457.

Platform differences: Same design is present across the respective ports, but physical message/order/collision events can cause normal invalidation/deconfliction at different times.

17. Can a committed future task disappear solely due to a new Top-K set?

Direct answer: Yes for algorithms that rebuild or repair future-plan state against the current candidate universe, especially HIPC and DGA. No for CBAA's single current destination; ACBBA/PI protect a valid retained prefix and use Top-K for refill. DMCHBA does not prune its active path solely on Top-K between triggers, but a triggered Hungarian rebuild can replace it.

Evidence: HIPC.py _build_bundle/_replace_own_bundle_if_changed lines 112-155 and 277-312; DGA.py current-path seeding/repair lines 283-304 and 383-420; DMCHBA.py lines 136-230.

Platform differences: Same category-level behavior is intended in HIL/physical ports. Collaborative HIL's different exact-tie order can change which future task enters a rebuilt plan.

18. Uniform restricted-set interface

Direct answer: Not fully. All allocators conceptually call a candidate-list method, but the executed implementation is not one single allocator-independent function. Base classes provide _filter_candidate_cells, optimized Bayesian classes use _packed_candidate_cells, native DMCHBA has _prepare_candidates, native collaborative has candidates, and physical programs duplicate per-algorithm candidate code.

Evidence: Bayesian base.py lines 125-157; memory_optimized.py lines 149-268; native Bayesian DMCHBA lines 358-453; native collaborative base.py lines 17-41; Hardware/Algorithms/Pololu_*.py candidate functions.

Platform differences: The claim "allocator-independent preprocessing concept" is supported. The stronger claim "one identical preprocessing implementation for all allocators/platforms" is not supported.

19. Exceptions, bypasses, protected tasks, duplicated logic

Direct answer: CBAA bypasses filtering while retaining a current assignment. ACBBA/PI filter only during bundle refill. Optimized PI caches one candidate list during a bundle build to avoid repeated filtering. HIPC and DGA request always-ranked candidate order. DMCHBA may call candidate construction for an assignment signature and for a triggered assignment in the reference path. Candidate logic is duplicated in native HIL and each physical file.

Evidence: memory_optimized.py PIOptimizationMixin lines 468-494; HIPC optimized lines 369-385; DGA.py lines 505-521; DMCHBA.py _assignment_input_signature lines 594-604 and _run_assignment lines 167-230; physical CBAA lines 1497-1521 as representative duplication.

Platform differences: These differences explain why filter-call counts vary within one algorithm/K condition and why not every choose_goal invocation executes the expensive allocation algorithm.

20. Direct effects on algorithm-specific state

Direct answer: Filtering directly changes the input task universe; downstream algorithm code then changes algorithm state. It can limit bundle/path refill, HIPC team-plan content, DMCHBA clone count and Hungarian matrix size, and DGA chromosome/population repair. It does not change configured horizon length itself and does not directly truncate global consensus/winner tables simply for being outside Top-K.

Evidence: ACBBA.py lines 97-157; HIPC.py lines 112-155 and 206-276; DMCHBA.py lines 179-230 (ceil(tasks/agents), matrix size); DGA.py lines 383-420. Consensus changes occur through normal algorithm message/repair code, not in base filter.

Platform differences: Native DMCHBA materializes packed task/matrix workspaces rather than Python structures; Collaborative native allocators use target slots. Logical downstream sensitivity remains, but representation differs.

D. FILTER IMPLEMENTATION AND TIMING BOUNDARIES
==============================================

21. Top-K selection algorithm

Direct answer:

Implementation/allocator                    Selection procedure
AGX Bayesian CBAA/ACBBA/PI/HIPC             Reusable arrays plus bounded insertion selection of the best K; not a heap. HIPC always ranks.
AGX Bayesian DMCHBA                          Full Python sorted(... ) when restricted.
AGX Bayesian DGA                             Prebuild/full-sort candidate tuples; restricted base path may sort again; optimized GA changes plan storage, not this candidate ranking.
AGX Collaborative                           Base full sort when restricted; HIPC/DGA pre-rank even when unrestricted.
RP2040 Bayesian generated four + DGA         Corresponding generated optimized code; bounded insertion for CBAA/ACBBA/PI/HIPC, DGA pre-sort behavior.
RP2040 Bayesian native DMCHBA                 Bounded insertion into a fixed-capacity uint16 candidate array.
RP2040 Collaborative                          Full list sort when restricted; HIPC/DGA always sort.
Physical Bayesian                             Full list sort and slice/delete in each standalone program; HIPC/DGA have their algorithm-specific pre-ranking behavior.

Evidence: memory_optimized.py lines 149-268; base.py lines 139-157; DGA.py lines 505-521; native Bayesian dmchba_complete.py lines 358-453; native collaborative base.py lines 17-41; physical CBAA lines 1497-1513.

Platform differences: The selected logical top K is usually equivalent, but asymptotic procedure and allocation behavior are not identical.

22. Execution order

Direct answer: The common logical order is (1) scan locally valid tasks, (2) perform validity checks, (3) obtain local probability, (4) compute Manhattan distance, (5) rank/select if needed, and (6) construct the returned candidate representation/list. Base implementations first build/copy an unrestricted list, then compute ranking keys inside sorted. Packed implementations combine scanning, validity, probability, and distance into one pass, then bounded-select, then construct coordinate tuples. Host/device serialization occurs after the timed allocator call in HIL.

Evidence: base.py lines 139-157; memory_optimized.py lines 218-268; native collaborative base.py lines 17-41; replay_worker.py lines 848-975.

Platform differences: AGX uses Python lists/tuples and optimized typed arrays; HIL uses typed arrays/bytearrays and bounded protocol output; physical uses local Python lists/tuples. Serialization is not part of filter time.

23. Contents of measured candidate-filter time

Direct answer: It measures the entire decorated/candidate method: candidate discovery, validity checking, probability and distance retrieval/calculation performed there, sorting/selection, truncation, and construction/copying of its return list. It is cumulative when one allocator call invokes the filter multiple times.

Evidence: Bayesian timed_candidate_filter wrapper, base.py lines 13-27; Collaborative wrapper, base.py lines 13-27; HIL nested sample sum, replay_worker.py lines 858-918; physical wrapper, CBAA lines 1516-1521.

Platform differences: perf_counter_ns is used on AGX; ticks_us/ticks_diff on HIL and physical. The wrapped implementations differ, so "filter time" measures the platform's actual filter implementation, not a normalized abstract operation.

24. Does filter timing include candidate generation/validity?

Direct answer: Yes. Timing starts before _candidate_cells/_packed_candidate_cells/native candidates scans for valid tasks. It does not begin after an already-built unrestricted set.

Evidence: timed_candidate_filter wraps the complete candidate method (base.py lines 13-27); memory_optimized.py decorator at line 218 followed by scan at lines 230-246; physical CBAA starts at line 1517 before _candidate_cells_impl.

Platform differences: Same boundary intent across platforms.

25. Allocation, copies, tuples, and garbage collection in filter timing

Direct answer: Any allocation, copying, tuple construction, and interpreter garbage collection that occurs while the timed filter method runs is included. No explicit gc.collect is called inside the HIL/AGX filter regions. Physical gc.collect is explicitly called before the trial-loop allocator call, so that explicit collection is excluded; an incidental automatic collection inside the filter would still be included.

Evidence: base.py lines 18-25 and list(candidates) at line 140; memory_optimized.py lines 152-157 and 265-268; physical CBAA trial loop lines 2040-2058.

Platform differences: Different object-allocation pressure and garbage collectors make the measured times platform-specific.

26. Allocator-exclusive time

Direct answer: Allocator-exclusive time is the elapsed enclosing choose_goal/pick_task_cell call minus the cumulative nested candidate-filter samples recorded during that same call. It includes the allocator's remaining state repair, scoring, consensus bookkeeping, optimization/Hungarian/GA work, decision/debug/message construction performed inside choose_goal, and incidental interpreter overhead. It excludes operations before/after the enclosing call.

Evidence: AGX robot.py lines 294-307; HIL replay_worker.py lines 871-933; physical timing helper and pick_task_cell wrapper, Hardware/Algorithms/Pololu_CBAA.py lines 161-189 and 1738-1744.

Platform differences: HIL times runtime.choose_goal on the RP2040; AGX times allocator.choose_goal in CPython; physical times the standalone allocator entry point. These are analogous boundaries but not identical code bodies.

27. Combined = filter + exclusive

Direct answer: Yes by construction, subject only to max(0, ...) protection:

    allocator_exclusive = max(0, combined_allocator_elapsed - cumulative_filter_elapsed)
    combined_allocator_elapsed = filter + allocator_exclusive

For valid nested samples where filter <= combined, the equality is exact in integer timer units.

Evidence: robot.py lines 300-307; replay_worker.py lines 907-933; physical record_allocator_time lines 174-189.

Platform differences: AGX stores nanoseconds then reports milliseconds; HIL/physical store microseconds.

28. Timer locations

Direct answer:

* AGX combined timer: robot.py lines 294-300, immediately around allocator.choose_goal. Filter timer: algorithms/base.py lines 13-27 around candidate discovery; allocator-exclusive subtraction: robot.py lines 301-307.
* RP2040 HIL combined timer: replay_worker.py lines 870-875 around runtime.choose_goal; filter samples are cleared/read at lines 858-918; exclusive subtraction at lines 929-933; PTIMED is emitted at lines 959-974 before result serialization.
* Physical combined timer: Pololu_CBAA.py pick_task_cell lines 1738-1744 and timing helpers lines 161-189; candidate timer lines 1516-1521. The other Pololu_*.py files use the same pattern around their allocator-specific entry points.

Evidence: Simulation/Architecture/simulator/benchmark_sim/core/robot.py lines 291-313; simulator/benchmark_sim/algorithms/base.py lines 13-27; allocator_replay/device/common/replay_worker.py lines 858-974; Hardware/Algorithms/Pololu_CBAA.py lines 161-189 and 1516-1744.

Platform differences: perf_counter_ns versus ticks_us; CPython versus MicroPython; physical calls occur only post-clue, while simulator choose_goal is invoked pre-clue for serpentine behavior but candidate filtering/allocation logic is inactive until the clue.

29. Excluded operations

Direct answer: Movement, sensing, A* path planning, simulator message-bus delivery, radio/USB transfer, host waiting, fixture/state decoding, and result serialization are outside the combined allocator timer. HIL peer-message callback application is performed during untimed state-delta setup; outbound-message draining and chunked response transmission are after PTIMED. A message object/queue entry constructed inside choose_goal is included, but actual transport is not.

Evidence: AGX robot.py bus pump lines 263-270, allocator timer lines 294-313, message publish line 322, A* planning lines 335-345; HIL replay_persistent.py apply_delta/events lines 347-415, choose_goal lines 417-428, drain_messages lines 430-438; replay_worker.py lines 959-975; transport.py lines 1174-1218.

Platform differences: Physical flush/radio service and motion are outside pick_task_cell, though real communication order can change subsequent allocator state. Host HIL call latency is not reported as device allocator time.

30. AGX versus RP2040 filter implementation

Direct answer: The ranking concept is mostly shared, but implementation parity is qualified. Optimized Bayesian AGX and generated Bayesian HIL use the same packed bounded-insertion logic for CBAA/ACBBA/PI/HIPC; DGA retains its algorithm-specific pre-sort; RP2040 DMCHBA is a separate packed native port. Collaborative AGX uses coordinate tuples and a full sort; Collaborative HIL uses slots/encoded IDs and a full sort, with the confirmed row-major tie-break difference. Physical Bayesian uses duplicated full sorts rather than the optimized bounded-selection implementation.

Evidence: memory_optimized.py lines 149-268; device/physical/factory.py lines 1-38; native Bayesian dmchba_complete.py lines 358-453; native collaborative base.py lines 17-41; build manifest source_provenance and module list in Simulation/Architecture/allocator_replay/builds/micropython_1_24_o0/manifest.json.

Platform differences: Algorithmic complexity, object allocation, numeric storage, and collaborative exact-tie semantics differ; the high-level probability/distance restriction rule is shared.

33. DGA parameters

Direct answer:

* Generations/iterations per reallocation trigger: 25.
* Population size: 30.
* Crossover probability: 0.7.
* Mutation probability: 0.3.
* Elite count: 2.
* Tournament size: default 3.
* Commitment horizon: 3.
* Fitness: maximum route cost + 0.05 * total route cost; each route edge uses probability-adjusted cost distance + 8*(1-normalized probability).
* Crossover: for each robot, concatenate random contiguous segments from the two parent routes, then repair.
* Mutation: uniformly choose move, swap, reinsert, reverse, or clean, then repair.
* Repair: retain each valid unique candidate at most once, discard entries outside the restricted candidate set, then append all missing candidates to the robot minimizing (append cost, current route length, robot ID).

Evidence: Simulation/Architecture/simulator/benchmark_sim/algorithms/DGA.py constants lines 39-48; fitness lines 219-240; crossover lines 306-334; mutation lines 336-381; repair lines 383-420; tournament lines 454-464. Shared probability-adjusted cost is base.py lines 176-283, with alpha=8 defined in AllocatorBase.

Platform differences: DGA_optimized.py packs population/routes into arrays and masks but retains the same constants/search procedure. Equivalence tests compare decisions, populations, fitness, and 25 generations in Tests/Simulation/Bayesian/test_dga_optimized_equivalence.py lines 129-227. Native Collaborative DGA is a separate MicroPython port; no physical DGA dataset exists.

35. RP2040 implementation changes

Direct answer:

* Build/runtime: modules are compiled to .mpy for MicroPython 1.24 with optimization level 0; CPython-only imports/type constructs are adapted by device/build.py. No motors/sensors/main.py initialization is included.
* Data structures: fixed-width arrays (notably uint16 cell IDs), bytearray masks, compact slot indices, and reusable workspaces replace many dictionaries/tuple collections.
* Numerical storage: explicit array('f'), array('d'), integer/fixed-point cost arrays, and scaled integer costs are used in native ports. The preflight confirms double-array support, but the width of every ordinary MicroPython float object is not established by source.
* Persistent state: one allocator/robot context remains resident; the host sends initial state then deltas/events. DGA RNG/population fields are streamed separately to bound memory.
* Hungarian: native Bayesian DMCHBA uses reusable packed workspaces and scaled integer/fixed-point costs rather than constructing the AGX Python matrix representation.
* GA: DGA_optimized stores plans/populations in packed arrays/masks; this optimization is also the production AGX class, not solely an RP2040 change. Collaborative HIL DGA is a separate native port.
* Sorting: packed bounded insertion for optimized Bayesian filters; native Collaborative uses list.sort over slots; native DMCHBA uses bounded insertion.
* Garbage collection: no explicit gc.collect is inside the HIL timed choose_goal/filter region. Automatic collection may occur and would be included.
* Native/viper: no @micropython.native or @micropython.viper decorator is used in the inspected replay allocator modules.
* Messages/protocol: allocator-specific peer messages are created on device. State/result fields are transported over ASCII framed, sequence-numbered, CRC-checked base64 chunks; PTIMED precedes result streaming.

Evidence: device/common/replay_persistent.py lines 273-438; device/common/replay_worker.py lines 848-975; host/transport.py lines 639-744, 1116-1218; native Bayesian dmchba_complete.py lines 1-110 and 358-453; native Collaborative state.py lines 66-100; DGA_optimized.py packed-plan/repair regions; build manifest fields compiled, optimization, safety, files, source_provenance.

Platform differences: AGX has effectively unconstrained host memory and CPython objects; HIL is explicitly memory-bounded. Physical programs also use typed arrays and explicit gc.collect, but their monolithic code and communication stack differ.

G. HIL ARCHITECTURE AND TIMING CAP
==================================

48. HIL execution path

Direct answer: The host runs mission dynamics: scenario loading, simulated movement, sensing, path planning, event scheduling, communication bus, and trial/watchdog logic. At each choose_goal trigger it snapshots the current logical robot/allocator state, sends an initial context or bounded delta plus queued peer/callback events to an RP2040, and waits. The RP2040 applies setup untimed, runs/times choose_goal, and returns PTIMED followed by goal, outbound allocator messages, and mutable post-state. The host applies that returned state, inserts returned messages into the normal simulator message path, and advances the mission. One complete logical trial remains on one board; no desktop shadow choose_goal controls decisions.

Evidence: Simulation/Architecture/allocator_replay/hil/campaign.py _run_trial, lines 94-230; hil/bridge.py AuthoritativeBridge call/apply region lines 409-795 and make_proxy_allocator lines 972-1064; device/common/replay_persistent.py lines 273-438; replay_worker.py lines 848-975.

Platform differences: AGX-only simulation executes allocator and environment in the same host process. HIL moves only allocator execution/state mutation to RP2040. Physical runs environment, sensing, motion, and allocator on four separate robots without host simulation.

49. Host-device interface

Direct answer: USB serial COM ports using a custom ASCII framed protocol. Bulk values are base64 chunks with sequence numbers, CRC32 validation, acknowledgements/retransmission, and bounded result streaming. Devices are identified by machine.unique_id rather than COM number in campaign records.

Evidence: host/transport.py imports/protocol helpers lines 3, 147-184; chunk upload lines 639-744; persistent chunk receive lines 1116-1167; HIL preflight devices array in device_preflight.json.

Platform differences: Physical peer communication uses the robot communication stack/UART topics, not this host replay protocol.

50. Peer-message generation and processing

Direct answer: Algorithm-specific peer messages are generated on-device as a consequence of choose_goal. The host mediates routing through the simulator's communication bus. When delivered to a recipient, the host queues the message as an event; the recipient RP2040 context applies the corresponding algorithm callback before its next timed choose_goal. Thus message semantics/state updates are on-device, while delivery scheduling is host-simulated.

Evidence: replay_persistent.py _apply_event lines 375-415 and drain_messages lines 430-438; hil/bridge.py accepted-message handling lines 672-794 and proxy queue_message/make_messages lines 972-1064.

Platform differences: AGX processes callbacks in the simulator process. Physical peers transmit/process messages on actual robots with real communication latency/order.

51. Preservation of scenarios, triggers, and event order

Direct answer: HIL uses the same scenario files/hashes and the same simulator runner, robot mechanics, allocator callback triggers, and logical event scheduler as the matching simulation. The proxy replaces choose_goal and allocator callbacks while leaving environment progression on the host. Hardware wall-clock delay does not advance simulated mission time. Exact allocator outputs can still diverge because the RP2040 ports/numerics/tie-breaks differ, which then changes subsequent simulated paths/events.

Evidence: campaign.py lines 94-158; bridge.py proxy factory lines 972-1064; HIL manifest scenario hashes and selected IDs.

Platform differences: Scenario/event framework parity is supported; identical end trajectories are not guaranteed and are explicitly what validation measures. Physical execution has genuinely asynchronous sensor/communication/motion events.

52. Unit to which the 30-second cap applies

Direct answer: One acknowledged, combined filter-plus-allocator choose_goal call. It is not an entire trial and not allocator-exclusive time alone.

Evidence: config/study.py lines 50-52; transport.py lines 1174-1203 starts the deadline after PCALL_READY and waits for PTIMED; replay_worker.py lines 871-874 times runtime.choose_goal including nested filtering.

Platform differences: The cap is HIL-only. AGX uses event caps for trial progression, not a 30-second allocator-call limit. Physical trials do not apply this HIL watchdog.

53. Watchdog versus censoring

Direct answer: Both. It is an execution watchdog that interrupts/resets a nonreturning device call, and it is a feasibility/censoring rule: a reproducible two-of-three timeout marks the condition timing_unusable_30s and prevents partial condition averages from being treated as representative.

Evidence: bridge.py attempt loop lines 458-720; report.py representative/condition aggregation lines 396-455; build_analysis_tables.m CapStopped lines 190-213 and feasibility lines 600-610.

Platform differences: HIL only.

54. What happens after a cap exceedance

Direct answer: The host records a timeout attempt, interrupts/resets/restarts the worker, reloads the persistent context from the clean pre-call snapshot, and retries the same call up to three total timing attempts. At least two timeout outcomes classify the condition timing_unusable_30s. Only that condition stops; transport failures are recovered/retried separately and do not count as timing attempts.

Evidence: bridge.py _restart_after_failed_attempt/_recover_attempt lines 350-408; attempt handling lines 458-720. transport.py ReplayTimeout and run_persistent_ready lines 1174-1203.

Platform differences: HIL only. Memory failures have a parallel reproducibility classification memory_unusable rather than timing_unusable.

Its raw attempt journal records timeout status, configured timeout_seconds, and host-side elapsed diagnostics near the deadline; true device choose_goal elapsed is unavailable because PTIMED never arrived. The trial generation remains incomplete/failed and is excluded from accepted timing summaries.

Evidence: hil/bridge.py _timeout_result lines 100-112 and call-attempt journal construction lines 163-257, timeout branch lines 525-546; hil/report.py accepted_for_analysis logic lines 294-316.

65. Exact analysis metric definitions

Direct answer:

* Mean combined time per call for a trial:

      CombinedPerCallMs = CombinedTotalMs / AllocatorCalls

  where CombinedTotalMs is team-summed enclosing allocator time and AllocatorCalls is team-summed calls.

* Cumulative allocator time per trial:

      CombinedTotalMs = sum of all combined allocator-call durations for all robots.

* Aggregate condition filter share:

      100 * sum(FilterTotalMs over valid trials) / sum(CombinedTotalMs over valid trials).

* Paired compute reduction at K relative to 100%:

      100 * (T_100 - T_K) / T_100.

  The code first computes percent change 100*(T_K-T_100)/T_100 and negates its mean for MeanComputeSavingPct.

* Paired max-step degradation:

      100 * (S_K - S_100) / S_100.

Evidence: build_analysis_tables.m standardized fields lines 120-182; safeDivide lines 272-275; condition filter share lines 374-382; paired changes lines 442-509.

Platform differences: The same analysis formulas consume simulation and HIL trial rows. Physical validation compares raw step differences, not K-versus-100% percent degradation.

Across a condition, the current condition table reports descriptive statistics of trial-level CombinedPerCallMs; raw simulator robot/system reports also retain per-robot and team totals.

Direct answer: HIL accepts raw call rows from completed accepted trial generations, groups them into robot-trial and system-trial rows, and calculates totals/statistics from those pooled call durations. Direct answer: It is a sum over all allocator calls from all four robots, not a mean or maximum. Separate maximum-call fields are also reported.

71. Statistical tests located

Direct answer: The current source-controlled MATLAB analysis performs:

* two-sided one-sample paired t-tests on paired K-versus-100% percentage changes;
* approximate Wilcoxon signed-rank tests on the same paired changes;
* Holm step-down adjustments across nonbaseline modes within mission/platform/algorithm/metric;

Those are timing-validation analyses, not the primary K-response tests.

72. Mission-performance changes across K

Direct answer:

Test: two-sided paired t-test, with approximate Wilcoxon signed-rank as a robust companion.
Repeated-measures structure: pair each restricted mode with R0/100% within the same TrialID; there is no single omnibus repeated-measures ANOVA across all K.
Pairing unit: scenario trial ID, separately within mission, platform, and algorithm.
Factors: K/Mode is the compared within-trial condition; algorithm, mission, platform, and metric define separate groups rather than factorial fixed effects.
Correction: Holm across all nonbaseline modes within each mission/platform/algorithm/metric.
Effect size/estimate: mean, SD, median, and t 95% CI of paired percent change. No standardized Cohen d or rank-biserial effect size is computed for this table.
Failures: only pairs with both completed, analysis-valid, finite values and nonzero baseline are used; pair completeness is reported.

Evidence: build_analysis_tables.m lines 442-590.

Platform differences: Same structure for AGX and HIL. HIL may have much lower pair completeness at hardware-stopped settings.

81. Support for "same candidate restriction and allocator behavior across platforms"

Direct answer:

Fully supported:
* Same mission-level candidate concept: locally valid unsearched Bayesian cells or locally incomplete known targets.
* Same fixed K values/bases for matching simulation-HIL conditions.

83. Concise methodology-ready implementation summary

Direct answer:

Value-ranked candidate restriction was applied only when an allocator's candidate-selection path executed. For probabilistic search, each robot formed its locally valid unsearched-cell set and ranked candidates lexicographically by descending local target probability, ascending Manhattan distance from its current cell, and ascending coordinate tuple. For Collaborative Visit, the same probability-distance rule was used; because active targets normally had equal value, distance was the effective primary key. The retained count K was fixed before each trial from the full scenario basis using K=max(1,int(Nr+0.5)), with N=361 grid cells for probabilistic search and N=50 initial targets for Collaborative Visit; K was not recomputed from the current candidate count. If no more than K valid candidates remained, all were retained.

The simulation study used a 19x19 grid, four robots starting at (0,0), (0,6), (0,12), and (0,18), six allocators, ideal communication, a one-task CBAA commitment, and horizon three for ACBBA, PI, HIPC, DMCHBA, and DGA. Bayesian simulation evaluated 500 common scenarios per allocator at K={1,4,11,18,36,90,181,271,361}; Collaborative Visit evaluated 100 common 50-target scenarios per allocator at K={1,2,3,5,13,25,38,50}. Candidate-filter time enclosed candidate discovery, validity checking, ranking-value calculation, selection/sorting, truncation, and returned-list construction. Combined allocator time enclosed choose_goal, and allocator-exclusive time was computed as combined time minus cumulative nested filter time. Movement, sensing, path planning, message-bus delivery, USB transfer, and result serialization were outside the timed region.

In Pololu-authoritative HIL, the host retained simulation mechanics and sent each current allocator state/callback set over USB serial to an RP2040. The RP2040 executed and timed choose_goal, returned the chosen goal, allocator messages, and mutable state, and the host applied that response before advancing the simulation. A 30-second watchdog applied to each combined choose_goal call; reproducible timeouts stopped only that condition and were retained as raw failed attempts rather than imputed timing values. The HIL ports used packed arrays and persistent contexts to fit RP2040 memory. Bayesian generated allocators were covered by reference-equivalence tests, whereas native DMCHBA and all native Collaborative ports were separate implementations; notably, Collaborative HIL used a row-major tie-break for exact ties rather than the simulator's coordinate-tuple order.

Trial-level maximum robot steps was the maximum of the four robot step counts and total team steps was their sum. Cumulative allocator time was the sum of all robot call durations, and mean time per call was that team total divided by the team call count. Primary K-versus-100% analyses paired completed, valid rows by TrialID and tested paired percentage changes using two-sided paired t-tests and approximate Wilcoxon signed-rank tests with Holm adjustment within mission, platform, algorithm, and metric. Absolute K=1 was retained for failure reporting but excluded from the primary performance, computation, and tradeoff modes.

Methodology qualification: The candidate-ranking concept and fixed K conditions are shared across platforms, but the implementation is not literally identical. Selection procedure, packed numeric representation, native ports, and physical standalone code differ, and Collaborative exact-tie ordering differs between AGX and HIL. These qualifications should accompany any cross-platform parity statement.

Evidence: Simulation/Architecture/simulator/benchmark_sim/algorithms/base.py lines 13-27 and 125-157; memory_optimized.py lines 149-268; simulator/core/robot.py lines 291-345; allocator_replay/config/study.py lines 8-52; allocator_replay/hil/bridge.py lines 409-795; device/common/replay_worker.py lines 848-975; Results/Analysis/value_ranked_candidate_restriction_matlab/build_analysis_tables.m lines 442-590 and 709-883.

Platform differences: The final paragraph states the qualification: the ranking concept, K, scenarios, and timing decomposition are shared where documented, while selection procedure, numerical representation, native ports, collaborative tie-breaking, and standalone physical code are not identical.
